## The game
Catch fish in the run lane north of the finish line (ten themed zones, each with a river and a guard animal), carry them home past the guard, put them in your plot's pool where they earn $/s. Speed (trained on your plot's treadmill, multiplied by trails) gates the zones; rods raise catch luck and speed. Slug `fish-and-run` (`GAME_SLUG`, override with `VITE_GAME_SLUG`).

Three.js (vanilla, no React) + Vite + Rapier (`@dimforge/rapier3d-compat`, wasm inlined; `main.js` awaits its init at top level, hence `build.target: 'es2022'`). Everything is procedural (canvas textures); the only imported model is the Bloxity base rig `public/avatars/player.glb`. Font: Fredoka (loaded in `index.html`).

- `npm run dev` / `npm run build`. `VITE_DEV_MODE=true` (see `.env.example`) skips the Bloxity SDK/CDN. Deploy: `.github/workflows/deploy.yml` uploads `dist/` to Bloxity Hosting (main = prod, dev = dev channel).
- All tunables are in `src/config.js` (the rest of `src/` holds no theme values). It now has: identity (`GAME_SLUG`, `GAME_TITLE`, `DEV_MODE`), the spawn (`SPAWN`, `SPAWN_FACING`), the hub (see **Hub** below), `MODES`, `PHYSICS`, `PLAYER_DIMS`, the look (`RENDER`, `FOG`, `TIME_OF_DAY`, `LIGHT`, `CHARACTER_COLORS`, `MATERIAL_PBR`, `GRAPHICS_PRESETS`, `BLOOM`, `NEON`, `graphicsPreset`), `TOUCH`, `CAMERA`, `SETTINGS`, and the rig (`RIG*`, `PROPORTIONS`, `ANIM`).
- All Bloxity SDK calls go through `src/bloxity.js` and must never throw (SDK may be blocked). It handles init/loading steps, auth (user/guest), settings (`graphics_quality`, `camera_sensitivity`, `show_fps`, `fullscreen`), avatar + proportion change events, the portal `respawn_request` event, the avatar customizer, and the matchmaker helpers the future net layer needs (`resolveServerEndpoint`, `locateRoom`, `updateRoom`).

## Mobile & responsive (required for every change)
The game must play on phones and tablets (portrait and landscape) as well as desktop. Treat a feature as unfinished until it works on touch and on a small screen.
- **Input**: every action needs a touch path, not just a key. Use Pointer Events (`pointerdown/move/up`, check `e.pointerType`), never mouse-only events. Layout (implemented in `src/touch.js`): left-thumb virtual joystick -> `inputState.move`, right-side drag -> `inputState.look`, on-screen buttons for jump/sprint/mode/etc., pinch -> `inputState.zoom`. Everything still feeds `inputState` in `src/input.js` so game code stays input-agnostic. Pointer lock does not exist on touch; never rely on it.
- **Detection**: decide touch UI with `matchMedia('(pointer: coarse)')` / `navigator.maxTouchPoints`, not the user agent. Show touch controls only on coarse pointers; a device can have both.
- **Layout/UI**: HUD and menus use relative units (`%`, `vw/vh`, `dvh`, `clamp()`) and flexbox/grid, no fixed pixel layouts. Tap targets >= 44px. Respect notches with `env(safe-area-inset-*)` (viewport already has `viewport-fit=cover`). Text readable at 360px width. No hover-only interactions. Add `touch-action: none` on the canvas and game controls so the browser does not scroll/zoom.
- **HUD layout on small screens**: `hud.js` `layout()` places the blocks round Boxity's reserved areas and the touch controls (transitions off while measuring), shrinking a block to 85% / 72% when it has no room at full size. The lane HUD (`laneHud.js` `anchor()`) lifts the Cast / Swing / action buttons (`--lane-bottom`) and the Click Fast bar + warning (`--lane-bottom-wide`) over whichever bottom blocks (backpack, event timer, cash column) their width crosses. `touch.js` keeps the top-right buttons under any reserved area reaching that corner (`--resv-t`; stacked in a column under 360 px wide). The Fish panel is a centred card in portrait and sits left of CAM / JUMP in landscape (`fishPanel.css`). Check with the 320x568, 360x640, 375x812, 667x375, 568x320 and 812x375 viewports.
- **Resize/orientation**: anything sized to the screen (camera aspect, renderer, HUD) must react to `resize` (covers orientation changes). Use `visualViewport` where the on-screen keyboard or browser bars matter.
- **Performance**: mobile GPUs are weak. Respect the `graphics_quality` presets in `src/config.js` (cap DPR, shadow map size, draw distance); default to a lower preset on coarse-pointer devices. Avoid per-frame allocations; keep draw calls and texture sizes low.
- **Testing**: check every UI/input change at a phone viewport (e.g. 375x812 and landscape 812x375) with touch emulation, plus desktop, before calling it done.

## Multiplayer, saves (net.js and friends; ported from Scare Your Neighbor)
- `net.js`: Colyseus link to the backend room `world` (matchmaker via `bloxity.resolveServerEndpoint`; `VITE_SERVER_URL` for a local server, see `.env.example`). The server holds the only save: `progress` hydrates every store, `noProgress` keeps the fresh state and saves it, `serverError` turns saving off. Saves the whole snapshot when it changed, at most every `NET.saveEvery` s and on tab hide/close; guests (`guest-` ids) are never saved; `VITE_DEV_MODE` plays as a per-tab `dev-` id, so two tabs are two players. Never throws, never blocks play: offline it keeps retrying.
- Stores (`setStores` in main.js, each `{ snapshot(), hydrate(doc) }`; the backpack before the Index): `activeFish.js` `snapshotFish/hydrateFish` (money, gems, lifetime `earned` / `caught`, `income` $/s, `slots`, `fish[] { species, weight, earn, mutation, equipped, hotbar }`; `inventory.loadInventory` replaces the backpack with new uids), `rods/state.js` (`rods[]`/`rod`), `trails/state.js` (`trails[]`/`trail`, "" = none), `speed.js` (`trained`), `fishIndex.js` (`unlocked[]`/`claimed[]`), `hub/treadmill.js` (`treadmill` level), plus the offline earnings: the server sends `offline` (income x offline rate x time away, max 24 h) and main.js grants it with a "Welcome back" toast.
- **Room size = plots**: `PLOTS.length` (8) players (backend `ROOM_MAX_CLIENTS`). The loading screen waits up to `NET.joinWait` s for the server's plot (`waitForBase`); main.js builds the hub with it (`buildHub({ myPlot })`; offline = `MY_PLOT`). There are no placeholder players: plots nobody owns stay empty, and the board shows only real rows (offline just yours). `setWantedBase` asks for the same plot on a rejoin.
- Presence (sent from main.js `sendPresence` every frame, throttled in net.js): `pose` { x, y, z, yaw, speed, vy, grounded, knocked (thrown by a guard) }, `loadout` { rod, trail, slot (0 none / 1 rod / 2 bat / 3 backpack fish), item (that fish's species), hold (species carried overhead out of the lane: `lane.carrying`) }, `setAvatar` (`syncAvatar` after each avatar load). `remotePlayers.js` draws everyone from the roster: Bloxity avatar, name tag, the tool in hand (`equipTool(avatar, slot, fish, rodId)`), the overhead catch with the lane's `POSE.carry`, lying flat while knocked, their trail ribbon; dead reckoning, nearest `NET.maxRemotes` first.
- Plots: every plot always has a treadmill + sign (`plots.js`); `dress(owner)` sets the tag, the pool's fish and the treadmill look. Twice a second main.js sends `plot` (JSON `{ f: active fish ids, t: treadmill look }`) and dresses every other plot from the roster (`plots.setOwner(i, owner | null)`).
- Bloxity trophy boards: `config.js` `LEADERBOARDS` (income, caught, earned) are declared by `bloxity.js` (`leaderboard.define`); the backend reports the saved scores (`platformBoards.ts`), the client never submits. Keep both lists equal. Custom characters (`equipped.characterId`) load through `avatar/look.js` `buildLook` for the player and the others alike. Gems are not wired to Bloxity.
- Leaderboard: the hub's MOST CASH/S board shows the server's `income` board (`onLeaderboard` -> `hub.board.setRows`).
- Bat bonks (`bat.js`, backend `bonk.ts`): client -> server `swing` { target? }, `giveFish` { weight }; server -> room `swing` { id } (everyone but the swinger), `bonk` { by, to, x, z, fish, byName, toName }; server -> attacker `gotFish` { species, weight, from }. Keep config `BAT.range` / `cooldown` / `immune` in step with backend `BONK`.
- Dev: `__game.net`, `__game.remotes`.
